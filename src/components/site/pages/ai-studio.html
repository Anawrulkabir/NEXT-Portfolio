The first version

The first version ran on AWS. When no machine had room for a new session, a workflow booted a new EC2 GPU instance. The instance installed its tools and joined a Kubernetes (K3s) cluster before an editor could start. Up to three users then shared its T4 GPU, and nothing stopped one of them using all 16 GB.

request creates reads / writes state live status
  1. AI Studio web appYou choose an editor and press launch. Status streams back live.
  2. API server (Go)Checks who you are and starts a launch workflow.
  3. TemporalRuns the launch and the cleanup. Machine state is kept in PostgreSQL; Redis queues tasks and credits.
  4. EC2 GPU instance, on AWSA spot g4dn (1× T4, 16 GB) boots and joins the K3s cluster. 5–10 minutes. Up to 3 users share it, with no isolation.
  5. IDE container + storage sidecarDeployed onto the instance. The sidecar mounts your files from S3 through JuiceFS.
  6. Ingress and secure tunnelReturn the workspace URL to your browser.

Why move

  • A new machine took 5–10 minutes to be ready, before the editor even started.
  • No memory isolation on the GPU: one heavy job could starve everyone else on the card.
  • Spot instances could be interrupted in the middle of a session.
  • Every instance cost money by the hour, even when it sat half used.
  • One instance type, one region, one GPU model.

The move

The platform moved to the company’s own GPU server: one 48 GB card, split by HAMi into six 8 GB slices. HAMi sits inside each container and refuses any GPU memory allocation past its slice, so six people can share the card without touching each other’s memory. Time-slicing alone, Kubernetes’ built-in way to share a GPU, can’t enforce that.

How a launch works now

The design the migration followed. Drawn from the post-prototype design document. Which details reached production is not yet confirmed.

  1. Web app → API serverLaunch with an editor and a duration.
  2. API server → TemporalStarts one workflow for the whole session.
  3. Temporal ↔ PostgreSQLChecks and deducts credits, then finds a free pre-started pod.
  4. Temporal → GPU serverAssigns the pod, starts the editor inside it, and checks it's ready.
  5. Workspace readyThe session is saved and the link returns to the browser.
  6. While you workThe browser sends a heartbeat every 5 minutes; the workflow waits for the timer, a stop, or silence.
  7. At the endThe editor stops, the pod goes back to the pool, unused credits are refunded.

Open questions in the design

  • Files live on one server’s volume, so a user moved to another server wouldn’t find them there.
  • A fixed pool of slices means a full server has to say “no capacity”, or queue, or fall back to the cloud.
  • Both the database and HAMi know which slices are in use; keeping two records in step is its own problem.
